# API contract

This is the contract the backend team implements. It's generated from Zod
schemas in `src/lib/contract/` — `openapi.json` at the repo root is the
machine-readable form, regenerated by `npm run generate:openapi` and kept
in sync by CI's `contract-drift` check (it regenerates and fails the build
if the committed file differs — the spec can't quietly fall behind the
code that defines it).

There is no backend yet. Everything below is a proposal grounded in what
the engine actually does (crawl → inspect → run → prove), not a spec
handed down from a UI mockup. Where something here is expensive or feels
wrong for how the engine actually works, **say so** — this is exactly the
kind of thing section 4 of `docs/PHASE_A.md` asks to negotiate rather than
silently implement around.

## Conventions

- **Auth.** Cookie-based (`cookieAuth` in `openapi.json`) — an httpOnly
  session cookie, set by a Next.js route handler that exchanges the
  magic-link token (see CLAUDE.md: the auth token never touches
  `localStorage` or JS-readable state). Every endpoint except `POST
/auth/*` and the public `GET /p/{token}` requires it.
- **Ids.** Opaque strings. Recommended, not enforced: a short type prefix
  plus a random suffix (`run_8f2a1c9d`, `scan_...`, `wksp_...`) — cheap for
  the engine to produce, self-describing in logs. The schema only requires
  a non-empty string, so this doesn't lock the backend into a specific id
  generator.
- **Timestamps.** ISO 8601 UTC, e.g. `2026-09-16T14:32:00Z`.
- **Errors.** `{ "error": { "code": "...", "message": "...", "details"?: ... } }`
  on every non-2xx response. `code` is stable and machine-readable;
  `message` is safe to show a customer as-is.
- **Pagination.** Cursor-based where a resource can grow unboundedly
  (`GET /runs`): `?limit=&cursor=` in, `{ data: [...], next_cursor }` out.
  Resources that don't grow the same way (`suites`, `targets`) are plain
  unpaginated arrays — cheaper for the backend, revisit if that stops
  being true.
- **Status vocabulary.** A run's per-step `status` uses the exact same six
  values as the design system's status tokens (`pass`, `fail`, `running`,
  `skipped`, `warning`, `queued` — see `styles/tokens.css` and
  `docs/DESIGN_SYSTEM_APP.md`). One vocabulary, engine to pixel, so there's
  never a translation table to keep in sync.

## Two decisions — settled

There is no backend team to sign these off (Phase A review, §3). These are
the frontend's position, written into the contract as requirements, not
suggestions. If a backend implementer later has a reason to push back,
that's a real conversation to have — until then, this is the spec.

### 1. SSE authentication for `GET /jobs/{id}/events` — cookie, with a deployment constraint

`EventSource` cannot send an `Authorization` header, and this product's
auth token deliberately lives in an httpOnly cookie it can't read anyway.
**Decision: cookie auth on the SSE request itself** — never a token in the
query string (tokens in URLs end up in server access logs, proxy logs,
and browser history; this is non-negotiable, not a style preference).

This decision has a constraint attached, and it's a deployment
requirement, not a suggestion: **`EventSource` does not send credentials
cross-origin without `withCredentials` plus matching CORS credential
headers**, and CLAUDE.md's architecture rule is that the browser talks to
the backend directly with no proxy in between to paper over that. So:

> **The API must be served from a sibling subdomain of the app** — e.g.
> `app.<domain>` and `api.<domain>` — with the auth cookie scoped to the
> parent domain. This makes the cookie same-site for both, and
> `EventSource` needs no special credential handling at all.

This is cheap to satisfy if the deployment topology is chosen with it in
mind, and expensive to retrofit after the fact (moving a live API to a
different subdomain, migrating cookie domain scope with users mid-session).
Whoever makes the hosting decision needs to know about this constraint
_before_ choosing where the API lives, not after.

`registry.ts` registers `cookieAuth` as the security scheme for this
endpoint; `src/lib/contract/events.ts`'s path description states the
subdomain requirement directly.

### 2. Screenshot URL security — two classes, authorization stated per endpoint, never a token in the URL

A screenshot of a customer's authenticated application is not public
data, even when it's embedded in a proof the customer chooses to share
externally. **Decision: two classes of screenshot, by which endpoint
serves them — never a bearer or session token embedded in the URL itself**
(URLs leak via referrer headers, server logs, browser history, and
copy-paste into tickets; this rules out "signed URL that's just a token in
a query string" too, not only the obviously-bad "session token in a URL"
case).

- **Session-scoped** (`GET /runs/{id}`, `GET /proofs/{id}` — inside the
  authenticated app): screenshot URLs are served from an authenticated
  endpoint, authorized by the session cookie exactly like any other API
  call. No separate signing scheme.
- **Proof-scoped** (`GET /p/{token}` — the public, unauthenticated proof
  page): the proof's own share token is already the capability that
  grants access to the page. Screenshots on it are **signed against that
  same proof token**, scoped to that one run, and **revoked the instant
  the proof is revoked**. A public proof page that still renders
  screenshots after its share link has been revoked is a bug, not an edge
  case to accept.

Same `Step`/`Proof` JSON shape either way — `screenshot_url` is always a
resolved, ready-to-fetch `url` string (`src/lib/contract/runs.ts`). The
backing authorization differs by which endpoint produced it, which is why
it's stated on each path's own description
(`src/lib/contract/runs.ts`'s `Step.screenshot_url`,
`src/lib/contract/proofs.ts`'s `GET /proofs/{id}` and `GET /p/{token}`
registrations) rather than once at the schema level — an implementer
reading only one endpoint's docs cannot get it wrong by omission.

## Endpoints

Every operation from `docs/PHASE_A.md`'s list is implemented — 30
operations across 12 resource groups, all present in `openapi.json`. Marked
**essential** (blocks a usable v1) or **nice-to-have** (v1 works without
it, or a manual workaround exists) — pushback on any of these is exactly
what this table is for.

### auth — essential, all four

Can't ship without sign-in. `POST /auth/magic-link`, `POST /auth/verify`,
`GET /auth/me`, `POST /auth/logout`.

### workspace

| Endpoint                      |              | Why                                                                                                                                   |
| ----------------------------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /workspaces`            | essential    | Nothing else works without one.                                                                                                       |
| `GET /workspaces/{id}`        | essential    | Poll status while it boots.                                                                                                           |
| `POST /workspaces/{id}/reset` | nice-to-have | `DELETE` + `POST` is a workaround for v1.                                                                                             |
| `DELETE /workspaces/{id}`     | essential    | Not customer-facing essential, but an _operational_ one — without it, engine processes leak and someone's infra bill grows unbounded. |

### scan

All three essential. `POST /scans`, `GET /scans/{id}` are the core
discovery flow; `POST /scans/{id}/continue` is essential, not an edge
case — most real applications are login-gated, so the parked/continue
handoff is on the critical path for a large share of targets, not a rare
exception.

### inspect

`POST /inspect` — essential. Coverage (`uniquely_locatable` per element)
is one of the product's two non-negotiable numbers (below); there's no
way to explain it to a customer without this endpoint.

### runs

| Endpoint                 |              | Why                                                                               |
| ------------------------ | ------------ | --------------------------------------------------------------------------------- |
| `POST /runs`             | essential    | The core action.                                                                  |
| `GET /runs`              | essential    | A run without a history view isn't testing-as-a-service, it's a one-off script.   |
| `GET /runs/{id}`         | essential    | Full step detail.                                                                 |
| `POST /runs/{id}/cancel` | nice-to-have | Letting a run finish instead of cancelling wastes some tokens but blocks nothing. |

**Run status includes `timed_out`, distinct from `failed`.** A run's
overall `status` is `queued` / `running` / `passed` / `failed` /
`cancelled` / `timed_out` — a different, run-level vocabulary from the
six-value step status above (a run's per-step statuses don't include
`timed_out`; only the run as a whole times out). `timed_out` means the
engine stopped responding and produced no further step events before the
deadline: a diagnostic absence, not a specific assertion failure, so it
carries no `message` the way a `failed` step does and `proof_id` stays
permanently null (no run report was produced). Surfaced by building the
mock's stateful lifecycle simulation (Phase A review §5) — the original
five-value enum had no way to represent an engine going silent, only an
engine that actively failed a check. Given the full design-token
treatment in `docs/DESIGN_SYSTEM_APP.md`'s "Isoluminance" section: its
own AA-verified color, its own icon (`ClockAlertIcon`, not `fail`'s
`OctagonXIcon`), and its own row in `src/lib/color/contrast.test.ts`'s
pairwise coverage — not `fail` with a different label.

### events

`GET /jobs/{id}/events` — essential. Watching a real browser execute
steps live is close to the product's core pitch; polling `GET
/runs/{id}` on an interval is a degraded fallback, not equivalent.

### suites

| Endpoint                          |              | Why                                                                                               |
| --------------------------------- | ------------ | ------------------------------------------------------------------------------------------------- |
| `GET /suites`, `GET /suites/{id}` | essential    | Need to see what was generated before running it.                                                 |
| `GET /suites/{id}/versions`       | nice-to-have | Version history is valuable but deferrable; most customers won't diff suite versions in week one. |

### targets

| Endpoint                                             |              | Why                                                                             |
| ---------------------------------------------------- | ------------ | ------------------------------------------------------------------------------- |
| `POST /targets`, `GET /targets`, `GET /targets/{id}` | essential    | Have to register what's under test.                                             |
| `PATCH /targets/{id}`, `DELETE /targets/{id}`        | nice-to-have | "Create a new target instead of editing" is a real, if annoying, v1 workaround. |

### proofs

| Endpoint                                    |              | Why                                                                                                                                                    |
| ------------------------------------------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `GET /proofs/{id}`                          | essential    | The auditable proof _is_ the product's deliverable — not optional.                                                                                     |
| `GET /p/{token}`, `POST /proofs/{id}/share` | nice-to-have | External sharing is a growth feature. The paying customer's own access to their proof (`GET /proofs/{id}`) already satisfies "get an auditable proof." |

### usage

| Endpoint            |              | Why                                                                                                                                           |
| ------------------- | ------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /usage`        | essential    | Test-token cost is called out as central to the value prop — customers need to see what they're spending, not just be billed for it silently. |
| `GET /usage/budget` | nice-to-have | A hardcoded plan limit works for v1; a dedicated budget/alert-threshold endpoint can wait.                                                    |

## The two non-negotiable shapes

Both are enforced by tests in `src/lib/contract/contract.test.ts`, not
just documented — a future edit that quietly makes either field optional
fails CI.

**Every run carries both `pass_rate` and `coverage`.** Pass rate alone is
misleading: the engine correctly declines to generate scenarios for
elements it can't uniquely locate, so a run can show 100% pass and still
have only tested a third of the page. `coverage.generated /
coverage.candidate` is what makes that visible. This applies to `RunSummary`
(the list view) too, not just `RunDetail` — the UI must never be able to
render one number without the other, including in a table of many runs.

**Every element in an inspect inventory carries `uniquely_locatable`.**
That boolean is what `coverage` is built from, and it's what explains to a
customer _why_ an element didn't get a test — not a vague "we couldn't
test everything," but a specific, honest reason per element.

## What this contract deliberately doesn't cover yet

- **Billing/payment.** Token _usage_ is in scope (`GET /usage`); how tokens
  get purchased is not — that's a different system with its own security
  surface (payment details), out of scope for a testing product's core API.
- **Team/org multi-user accounts.** Everything here is single-user-per-
  workspace. If multi-seat accounts are near-term, that's a real,
  contract-shaping conversation to have before the backend builds this,
  not an additive change layered on after.
- **Webhooks/notifications.** SSE covers "watch a job while the tab is
  open." Anything about "notify me when a run finishes and I'm not
  looking" is a separate, unaddressed concern.
